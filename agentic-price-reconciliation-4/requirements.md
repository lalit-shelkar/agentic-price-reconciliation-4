# Requirements

> **Purpose:** business-level "what and why." Defines the problem, goal, scope, and
> success criteria this project is judged against. Read this before any other file
> to understand why the design decisions elsewhere were made.

## 1. Problem statement
When a price/barrier status generated by the pricing system disagrees with a
counterparty's quoted price on a trade, a Mid-Office Analyst currently detects the
mismatch, manually pulls prices from three systems, finds the correct contractual
fixing source, drafts an unstructured email, waits an unbounded time for a reply,
escalates ad hoc if disputed, and manually logs everything. This is slow
(~75+ minutes of hands-on work before any wait time), inconsistent, and carries
weak audit-trail / FINMA compliance risk.

## 2. Goal
Replace the manual execution of this process with two cooperating agents
(Agent 1: detect → classify → draft comms; Agent 2: parse response → resolve →
close), with a human analyst retained only at two defined checkpoints, not as the
executor of every step.

## 3. In scope
- Automated detection of a price/barrier mismatch from counterparty correspondence
  and internal pricing feeds.
- Automated retrieval of prices (Bloomberg, Reuters, SIX) and the governing term sheet.
- Automated case creation, structured outbound communication (human-approved),
  inbound response parsing.
- Automated straight-through closure on agreement; structured, non-dead-end
  escalation on dispute.
- Full audit logging at every step for regulatory (FINMA) compliance.

## 4. Out of scope (v0.1)
- Actual trade booking/settlement system changes beyond updating pricing/break records.
- Legal determination of contractual disputes (agents flag; humans/Legal decide).
- Asset classes beyond barrier-triggered FX/rates products priced off
  Bloomberg/Reuters/SIX (extend later).

## 5. Success metrics

| Metric | AS-IS baseline | TO-BE target |
|---|---|---|
| Analyst hands-on time per case | ~75 min | ~5–10 min |
| Time to first outbound comms | Hours (queued) | < 20 min |
| % cases with complete structured audit trail | Low/inconsistent | 100% |
| Counterparty response SLA adherence | Not tracked | Tracked, target ≥ X% |
| % disputes with consistent escalation path | Inconsistent (ad hoc) | 100% |
| Straight-through (auto) closure rate | 0% | 60–80% of agreed cases |

## 6. Open questions (resolve with stakeholders before build)
1. Divergence tolerance (bps) that defines a real break vs. noise, per product type.
2. Auto-close notional/risk threshold — which trades qualify for full straight-through
   closure vs. mandatory light-touch human confirmation.
3. Counterparty response SLA — contractually defined already, or does the firm need
   to set/communicate it?
4. System of record for booking updates — which system does Agent 2 write to, and
   what's the existing API/access pattern?
5. Model risk governance — does this fall under existing MRM policy given it makes
   price-reconciliation decisions? Likely yes given FINMA context.
6. Term sheet repository — structured/searchable today, or does retrieval need a
   separate document-extraction project first?
7. Clarification-loop counter (see `10-error-and-exception-spec.md`) — does it reset
   when the counterparty provides materially new information, or always count toward
   the same hard cap?
